# ShopKart Security

## 1. Overview

ShopKart integrates security practices across the software development and deployment lifecycle.

Security controls are applied at multiple layers:

```text
Source Code
     │
     ├── Gitleaks
     ├── SonarQube
     └── Snyk
     │
     ▼
Docker Build
     │
     └── Hadolint
     │
     ▼
Container Image
     │
     └── Trivy
     │
     ▼
Amazon ECR
     │
     ▼
Amazon EKS
     │
     ├── IAM
     ├── Secrets Manager
     ├── External Secrets
     └── Kubernetes Security
````

The objective is to identify security issues as early as possible and reduce the use of long-lived credentials.

---

# 2. Security Controls

The project uses the following security tools and mechanisms:

| Control                   | Purpose                                |
| ------------------------- | -------------------------------------- |
| Gitleaks                  | Detect exposed secrets                 |
| SonarQube                 | Source-code analysis                   |
| Snyk                      | Dependency vulnerability scanning      |
| Hadolint                  | Dockerfile analysis                    |
| Trivy                     | Container image vulnerability scanning |
| AWS OIDC                  | Short-lived AWS authentication         |
| IAM                       | AWS authorization                      |
| AWS Secrets Manager       | Secure secret storage                  |
| External Secrets Operator | Synchronize AWS secrets to Kubernetes  |
| Kubernetes                | Workload isolation and access control  |

# 3. Gitleaks

Gitleaks scans the Git repository for accidentally committed secrets.

Examples of sensitive information that should not be committed:

```text
AWS Access Keys
AWS Secret Keys
Database Passwords
API Keys
Private Keys
JWT Secrets
Application Credentials
```

The security flow is:

```text
Developer
    │
    ▼
Git Commit / Pull Request
    │
    ▼
Gitleaks
    │
    ├── No detected secret → Continue
    │
    └── Secret detected → Investigate / Fix
```

The repository also contains:

```text
.env.example
```

for documenting required environment variables without committing actual credentials.

---

# 4. SonarQube

SonarQube performs static source-code analysis.

It helps identify:

* Bugs
* Vulnerabilities
* Code smells
* Code duplication
* Maintainability issues
* Test coverage information

The project configuration is maintained in:

```text
sonar-project.properties
```

Coverage generated by Jest can be supplied to SonarQube through LCOV reports.

Example:

```text
coverage/lcov.info
```

---

# 5. Snyk

Snyk is used for dependency security scanning.

The Node.js services use:

```text
package.json
package-lock.json
```

Snyk analyzes application dependencies against known vulnerability databases.

Pipeline flow:

```text
Node.js Application
       │
       ▼
package.json
       │
       ▼
Snyk
       │
       ▼
Dependency Vulnerability Results
```

The CI pipeline can use:

```bash
snyk test
```

for CI-time vulnerability testing.

It can also use:

```bash
snyk monitor
```

to maintain the project in Snyk for ongoing monitoring.

# 7. Hadolint

Hadolint analyzes Dockerfiles for common issues and recommended Docker practices.

Flow:

```text

    │
```

Flow:

```text

    │
```

# 9. AWS OIDC

GitHub Actions authenticates with AWS using OpenID Connect.

Instead of storing permanent AWS access keys in GitHub Actions, the workflow obtains temporary AWS credentials through an IAM role.

Architecture:

```text
                 GitHub Actions
                       │
                       │ OIDC Token
                       ▼
                AWS STS
                       │
                       │ AssumeRoleWithWebIdentity
                       ▼
                  IAM Role
                       │
              ┌────────┼────────┐
              │        │        │
              ▼        ▼        ▼
             ECR      S3       AWS APIs
```

The GitHub Actions workflow requires:

```yaml
permissions:
  id-token: write
  contents: read
```

The OIDC provider is:

```text
https://token.actions.githubusercontent.com
```

The AWS STS audience is:

```text
sts.amazonaws.com
```

---

# 10. IAM

AWS IAM controls which AWS resources the CI/CD workflow can access.

The GitHub Actions OIDC role should follow the principle of least privilege.

The role should only receive the permissions required by the pipeline.

For example, an image publishing workflow requires permissions related to Amazon ECR rather than unrestricted AWS administrator permissions.

---

# 11. Amazon ECR

Docker images are stored in Amazon ECR.

Application repositories include:

```text
shopkart/auth-service
shopkart/catalog-service
shopkart/order-service
```

The workflow authenticates to ECR using the AWS role obtained through OIDC.

Flow:

```text
GitHub Actions
      │
      ▼
AWS OIDC
      │
      ▼
IAM Role
      │
      ▼
Amazon ECR
      │
      ▼
Container Images
```

Images are tagged using the Git commit SHA.

Example:

```text
shopkart/order-service:<git-sha>
```

This provides traceability between source code and the container image.

# 12. Secrets Management

Application secrets should not be stored directly in Git.

ShopKart uses AWS Secrets Manager as the external secret store.

Architecture:

```text
                    AWS
                     │
                     ▼
            AWS Secrets Manager
                     │
                     ▼
       External Secrets Operator
                     │
                     ▼
            Kubernetes Secret
                     │
                     ▼
              Application Pod
```

This allows sensitive configuration to remain outside the application source code.

---

# 13. External Secrets Operator

External Secrets Operator retrieves secrets from an external secret management system and creates the corresponding Kubernetes Secret.

In this project:

```text
AWS Secrets Manager
        │
        ▼
External Secrets Operator
        │
        ▼
Kubernetes Secret
```

The Helm chart contains resources related to:

```text
ClusterSecretStore
ExternalSecret
ExternalSecret JWT configuration
```

This allows application pods to consume required secrets without storing their values in Git.

# 14. Database Security

PostgreSQL is used as the persistent database.

In the AWS deployment, the database is intended to remain private rather than being exposed directly to the public internet.

Network flow:

```text
Internet
   │
   ✕
   │
   └──────────────► RDS

EKS
 │
 └──────────────► RDS :5432
```

Access to PostgreSQL should be controlled through AWS security groups.

Only required application workloads should be permitted to connect to the database.

---

# 15. Redis Security

Redis is used by the application for:

* Shopping carts
* Catalog caching

Redis should remain accessible only to the application workloads that require it.

It should not be exposed directly to the public internet.

Expected architecture:

```text
Internet
   │
   ✕
   │
   Redis

ShopKart Pods
     │
     ▼
   Redis
```

# 16. Kubernetes Security

The application runs inside Amazon EKS.

Application workloads are isolated using Kubernetes namespaces and workload resources.

The Helm chart manages Kubernetes resources including:

```text
Deployments
Services
Ingress
Secrets
ConfigMaps
ServiceMonitors
```

Kubernetes access should follow the principle of least privilege.

# 17. Network Security

The AWS infrastructure uses public and private network segments.

High-level network design:

```text
                    Internet
                       │
                       ▼
               Public Subnets
                       │
                       ▼
                      ALB
                       │
                       ▼
                Private Subnets
                       │
                 ┌─────┴─────┐
                 │           │
                 ▼           ▼
                EKS         RDS
```

The public-facing entry point is the Application Load Balancer.

Application workloads and database resources are kept within the private network where appropriate.

# 20. Security in the Development Lifecycle

Security checks are integrated into the CI/CD pipeline instead of being treated as a separate final-stage activity.

```text
                Source Code
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
    Gitleaks    SonarQube      Snyk
        │           │           │
        └───────────┼───────────┘
                    ▼
               Docker Build
                    │
             ┌──────┴──────┐
             ▼             ▼
         Hadolint        Trivy
             │             │
             └──────┬──────┘
                    ▼
                 ECR
                    │
```

This approach is commonly referred to as shifting security checks earlier in the software development lifecycle.

# 22. Security Design Principles

The project follows these security principles:

### Least Privilege

AWS IAM roles should only receive the permissions required for their workload.

### No Long-Lived CI Credentials

GitHub Actions uses AWS OIDC instead of permanent AWS access keys.

### Externalized Secrets

Sensitive values are stored outside the Git repository.

### Private Infrastructure

Database and internal services should not be directly exposed to the public internet.

### Automated Security Scanning

Security checks are integrated into CI/CD.

### Image Traceability

Container images are tagged using Git commit identifiers.

### Defense in Depth

Security is applied at multiple layers rather than relying on a single security mechanism.
